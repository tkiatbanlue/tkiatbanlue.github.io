# UnitWise — Implementation Plan

## 1. Product goal
Build a fun, lightweight, mobile-first web app for families and friends to compare the real unit cost of household products. A shopper photographs a price tag or package, verifies extracted price and quantity, adds another product, selects a common comparison amount, and shares the result.

**Product promise:** Snap → Correct → Compare → Share.

This is a casual utility, not a retailer price aggregator, inventory tracker, or shopping marketplace.

## 2. Reference design
Use the previously generated three-screen UnitWise mockup as visual direction:
1. Home: friendly household-goods illustration, prominent **Take a Photo** and **Add Manually** actions.
2. Add Product: photo preview, editable price, quantity, and unit, plus add action.
3. Compare: side-by-side product cards, lowest unit price highlighted in green, adjustable comparison amount, savings summary, share action.

Visual language: Flaticon-inspired flat vector icons (original or properly licensed), rounded cards, thick navy outlines, blue primary buttons, pale blue surfaces, green savings highlights, large legible numbers. Do not copy proprietary Flaticon artwork without a license. Optimize for 360–430 px wide phones; scale gracefully to tablets and desktops. Thai baht by default; bilingual-ready UI.

## 3. Technology
- React + TypeScript + Vite
- Tailwind CSS
- Lucide icons plus original SVG household illustrations
- Tesseract.js for browser-based OCR (English and Thai where feasible)
- Browser camera/file input via `<input type="file" accept="image/*" capture="environment">`; provide normal gallery upload fallback
- localStorage for unsent draft products and recent comparisons
- Native Web Share API with clipboard fallback
- PWA manifest and service worker for installability and offline manual comparisons
- Static deployment on Cloudflare Pages or equivalent

No server, database, login, payment integration, analytics SDK, or ad SDK in MVP.

## 4. User journeys
### A. Photograph product
1. Tap **Take a Photo**.
2. Capture or upload price tag/package.
3. OCR proposes product name (optional), numeric price, numeric amount, and unit.
4. Show extraction confidence or flag ambiguous values; **never silently commit OCR guesses**.
5. User reviews and corrects fields, then taps **Add Product**.
6. Return to comparison, where user can add more products.

### B. Manual entry
1. Tap **Add Manually**.
2. Enter optional product name, price, amount, and unit.
3. Save to current comparison.

### C. Compare
1. Show 2–6 products in a comparison session (allow first product to be entered before a comparison exists).
2. Normalize compatible units: mL ↔ L, g ↔ kg, piece ↔ piece, wash ↔ wash.
3. Display unit price (e.g. ฿/100 mL) and equivalent cost at chosen comparison amount.
4. Default target: 1 L for liquids, 1 kg for mass, 1 piece for counts, 1 wash for wash counts. Allow user to change numeric amount and unit.
5. Mark lowest equivalent unit cost and show absolute/percentage savings versus the highest-cost item or a selected baseline; label comparison basis explicitly.
6. Offer **Share Result** using a concise text summary and optional future share-card image.

## 6. Data model
```ts
type Unit = 'ml' | 'l' | 'g' | 'kg' | 'piece' | 'wash';
type UnitFamily = 'volume' | 'mass' | 'count' | 'wash';

type Product = {
  id: string;
  name: string;
  priceTHB: number;
  quantity: number;
  unit: Unit;
  imageDataUrl?: string; // temporary preview only; do not persist large images
  source: 'ocr' | 'manual';
};

type Comparison = {
  products: Product[];
  targetQuantity: number;
  targetUnit: Unit;
};
```
Use stable IDs. Store only compact, validated product data in localStorage. Prefer not to persist photographs.

## 7. Calculation specification
Normalize to base units: mL, g, piece, wash.

```
baseQuantity = quantity * conversionFactor(unit)
pricePerBaseUnit = priceTHB / baseQuantity
equivalentCost = pricePerBaseUnit * targetBaseQuantity
savingsTHB = baselineEquivalentCost - bestEquivalentCost
savingsPercent = savingsTHB / baselineEquivalentCost * 100
```

Rules:
- Compare only within the same unit family; show clear explanation for incompatible units.
- Do not compare mL and g by assuming equal density.
- Require finite nonnegative price and strictly positive finite quantity/target.
- Use unrounded values for all calculations; round to 2 decimals only for display.
- For ties within a small numerical tolerance, report a tie rather than inventing a winner.
- Show "equivalent cost for X"; do not misrepresent it as actual checkout/package price.
- Distinguish **cheaper per unit** from **lower package price**.
- OCR is an input convenience; calculation never relies on language-model arithmetic.

**Example fixture:**
- Detergent A: ฿129 / 650 mL = ฿19.846... per 100 mL; ฿198.46 per L.
- Detergent B: ฿169 / 900 mL = ฿18.777... per 100 mL; ฿187.78 per L.
- B saves ฿10.68 per L versus A, approximately 5.4% relative to A.

## 8. OCR design
Implement OCR as an optional, fallible helper:
- Process the user-selected image in browser when possible.
- Extract candidate numbers and units using parsing rules for Thai/English labels: `฿`, `บาท`, `THB`, `ml`, `mL`, `ลิตร`, `L`, `g`, `กรัม`, `kg`, `กก.`, `ชิ้น`.
- Price tags may contain multiple numbers (original price, promotion, membership price, SKU); if ambiguous, ask the user to select or edit the correct price.
- Packaging may not show a price; let users enter it manually.
- Display a clear fallback when OCR fails or browser permissions are denied.
- Avoid sending photos to third parties.
- OCR model downloads may require connectivity initially; manual entry remains functional offline.

## 12. Acceptance tests
1. A 650 mL/฿129 product and 900 mL/฿169 product produce the fixture results above.
2. Changing comparison amount from 1 L to 500 mL halves equivalent costs, without changing the winner.
3. L and mL, kg and g normalize correctly.
4. mL and g cannot be ranked against one another.
5. Zero/negative/NaN quantity is rejected with a helpful message.
6. OCR mistakes can always be corrected before saving.
7. Camera denied, OCR unavailable, or offline: manual workflow still works.
8. Sharing produces a readable, accurate summary even when Web Share is unsupported.
9. Reload preserves product entries but not large photos.
10. Usable on a 360 px phone without horizontal overflow.

## 13. Agent execution rules
- Deliver a working app, not only a visual prototype.
- Implement deterministic calculations and tests before OCR integration.
- Keep dependencies minimal and avoid introducing a backend.
- Do not add ads in the initial build.
- Do not invent store prices or pretend OCR extraction is always accurate.
- Use the mockup as visual inspiration, not as a substitute for accessible responsive UI.
- At completion, provide install/run commands, test results, deployment instructions, and any known limitations.

## 14. Definition of done
A user can open the web app on a phone, manually enter or photograph two household products, confirm the detected numbers, change the comparison quantity, see which is cheaper per equivalent unit, and share the result. The app runs without a login or paid service.
